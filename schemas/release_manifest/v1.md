# `circuitc.release_manifest` schema version 1

The release manifest is strict compact canonical JSON followed by one LF. It is
the completion sentinel for one immutable release directory. The root contains
exactly these fields in this order:

1. `schema_name`: `"circuitc.release_manifest"`
2. `schema_version`: `1`
3. `release_identity_sha256`: exact release identity from the request
4. `request`: binding for the exact canonical `request.json`
5. `source`: exact source binding repeated from the request
6. `design_identity_sha256`: complete canonical Design identity
7. `applicability`: exact applicability repeated from the request
8. `tools`: exact ordered tool inventory repeated from the request
9. `validations`: ordered validation outcomes
10. `artifacts`: exact path-sorted artifact inventory from the request
11. `all_pass`: `true`

The request binding contains exactly `path`, `byte_length`, and `sha256` and
must name `request.json`. Validation rows contain exactly `capability`,
`evidence_role`, and `outcome`. Version 1 requires passing rows for source
elaboration, Design identity, catalog freshness, product artifacts,
fabrication inventory, ERC, DRC, unconnected items, schematic parity, and the
complete artifact inventory. Simulation and route-acceptance rows are present
exactly when those capabilities apply. No failed, unsupported, unevaluated, or
unknown outcome can appear in a manifest.

The manifest path is fixed as `manifest.json` and is excluded from the
artifact array to avoid a self-digest cycle. Its bytes are independently
reconstructed from current authoritative inputs. Unknown, missing, duplicate,
reordered, non-canonical, over-limit, or trailing data is invalid.

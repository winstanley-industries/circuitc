# CircuitC product resolution v1

## Status and authority

Version 1 is the canonical Layer-3 resolution spine for one exact product
variant. CircuitC source and canonical Design IR own product intent; the exact
pinned catalog snapshot owns authenticated observations. This artifact is a
deterministic compiled projection and cannot add or alter either authority.

## Encoding, path, and bounds

The artifact is compact UTF-8 JSON produced by `serde_json::to_string`, followed
by exactly one LF. Objects use the field order below. Unknown, missing,
duplicate, reordered, pretty-printed, trailing, or otherwise non-canonical
fields or bytes are invalid. A strict consumer parses, validates, canonically
reserializes, appends LF, and requires byte equality.

The complete artifact is at most 67,108,864 bytes including LF and contains at
most 10,000 component rows. The row ceiling is checked before expanded row and
join validation. No oversized artifact is truncated or partially accepted.
The checked sum of the complete resolution, BOM, placement, and assembly bytes
is also at most 67,108,864 bytes and is preflighted before any bundle path or
bytes are returned.

`variant_identity_sha256` is lowercase SHA-256 over ASCII
`CIRCUITC-PRODUCT-VARIANT-IDENTITY-V1`, one NUL byte, and the exact UTF-8
`variant_path`, in that order. The only valid artifact path is
`product/<variant_identity_sha256>/resolution.json`.

`product_input_sha256` is lowercase SHA-256 over ASCII
`CIRCUITC-PRODUCT-INPUT-V1`, one NUL byte, and then the compact canonical UTF-8
JSON bytes, without a final LF, of this exact input projection in field order:

- root `design_name`, `catalog_snapshot_id`, `catalog_snapshot_sha256`,
  `catalog_evaluated_on`, `variant_path`, `build_quantity`, `configurations`,
  and `components`;
- each configuration has `key` and `value` and is sorted by key; and
- each physical component has `component_path`, `reference`,
  `logical_function`, base `manufacturer`, `manufacturer_part_number`,
  `package`, `value`, `lifecycle_requirement`, `sourcing`,
  `approved_substitutions`, `x_nm`, `y_nm`, `rotation_degrees`, `side`, `state`,
  and `alternate_identity`, in that order, and components are sorted by path.

The value object has exact `kind`, `coefficient`, `exponent`, and `unit`.
`sourcing` has exact `minimum_available_quantity`,
`maximum_lead_time_days`, and `required_region`. Approved substitutions are
sorted exact objects with `manufacturer`, `manufacturer_part_number`, and
`package`. `alternate_identity` has those same fields only for `alternate` and
is null for `fitted` or `not_fitted`. The projection is constructed from typed
Design and selected-variant fields only; source text, source spans, Rust Debug
output, host state, and filesystem paths never enter the preimage.

## Root object

The root has exactly these fields in this order:

| Field | Type | Contract |
| --- | --- | --- |
| `schema_name` | string | Exactly `circuitc.product_resolution`. |
| `schema_version` | u32 | Exactly `1`. |
| `design_name` | string | Exact safe Design artifact stem. |
| `variant_path` | string | Exact canonical semantic path of one authored variant. |
| `variant_identity_sha256` | string | Recomputed variant identity above. |
| `product_input_sha256` | string | Recomputed authoritative-input projection digest above. |
| `catalog_snapshot_id` | string | Exact authenticated snapshot ID. |
| `catalog_snapshot_sha256` | string | SHA-256 of exact canonical snapshot bytes including LF. |
| `catalog_evaluated_on` | string | Exact authored Design IR evaluation date. |
| `build_quantity` | u64 | Exact positive variant build quantity. |
| `configurations` | array | Configuration entries strictly sorted and unique by `key`. |
| `components` | array | Physical-component rows strictly sorted and unique by `component_path`. |

The catalog fields must equal the `CatalogEvidenceRef` that authenticated the
exact snapshot. `catalog_evaluated_on` is a real `YYYY-MM-DD` date already
verified inside the snapshot validity interval. The root variant, build
quantity, and configurations equal the exact authored variant.

## Configuration entry

Each configuration has exactly `key` and `value`, in that order. The key is the
exact canonical token from Design IR and the value is exact non-empty canonical
text. Entries are strictly increasing by UTF-8 byte order of `key`; duplicate
keys are invalid.

## Physical identity and exact value

A physical identity has exactly these fields in this order:

| Field | Type | Contract |
| --- | --- | --- |
| `logical_function` | string | Exact canonical logical-function token. |
| `manufacturer` | string | Exact non-empty canonical text. |
| `manufacturer_part_number` | string | Exact non-empty canonical text. |
| `package` | string | Exact non-empty canonical text. |
| `value` | object | Exact typed value below. |

The value object has exactly `kind`, `coefficient`, `exponent`, and `unit`, in
that order. `kind` is `resistance` or `dc_voltage`; coefficient is `i64`;
exponent is the canonical Design IR `i8` decimal exponent; unit is respectively
`ohm` or `volt`. The object must equal the canonical Design component value
without floating-point conversion or dimensional coercion.

## Component row

Each component row has exactly these fields in this order:

| Field | Type | Contract |
| --- | --- | --- |
| `component_path` | string | Exact canonical physical-component semantic path. |
| `reference` | string | Exact canonical Design component reference. |
| `state` | string enum | `fitted`, `not_fitted`, or `alternate`. |
| `base_identity` | object | Exact primary physical identity and value. |
| `selected_identity` | object or null | Exact selected physical identity and value, or null under the rule below. |

Every physical Design component appears exactly once and virtual components
never appear. Rows are strictly increasing by UTF-8 byte order of
`component_path`; paths and references are unique exactly as required by the
validated Design.

State and selection obey these exact rules:

- `fitted`: `selected_identity` equals `base_identity`;
- `alternate`: `selected_identity` uses one exact authored approved alternate
  and inherits the component's exact logical function and typed value; and
- `not_fitted`: `selected_identity` is null.

Every base and approved alternate has been re-resolved against the exact pinned
snapshot. An alternate row exists only after exact Layer-2 function, package,
value, lifecycle, region, quantity, and lead-time checks pass.

## Verification and failure

The strict bundle verifier revalidates Design IR, re-authenticates the exact
catalog snapshot bytes, resolves all primary and approved identities, resolves
the exact variant, recomputes every root field and row, and requires exact
canonical byte equality. It rejects stale catalog fields, wrong variant
identity, missing, duplicate, reordered, virtual, or extra rows, inconsistent
state/selection, and any coordinated row set not derived from Design.
Its row selection, grouping, placement, quantities, and reconciliation are
independently implemented and do not call the emitter's corresponding helpers;
only primitive parsing, canonical serialization, checked arithmetic, and
digest functions may be shared.

Failure returns stable machine-readable diagnostics and no partial resolution.
This artifact is not a BOM, placement-host file, assembly-host instruction,
manufacturing result, or release evidence.

# CircuitC product catalog snapshot v1

## Status and authority

Version 1 is the active strict offline evidence contract for EPIC-0005 product
catalog verification and resolution. CircuitC source and canonical Design IR
own product intent. This snapshot owns only authenticated, point-in-time
catalog observations; it cannot add an approved substitute or relax a Design
constraint.

The contract exposes parsing, exact-byte authentication, and deterministic
resolution only. It is not a BOM, purchasing instruction, manufacturing
artifact, analysis report, release manifest, or release-publication contract.

## Canonical JSON encoding and bounds

The artifact is compact UTF-8 JSON produced by `serde_json::to_string`, followed
by exactly one LF. There is no indentation, byte-order mark, leading or
trailing whitespace, or trailing data. Object fields appear in the declaration
order documented below. Unknown, missing, duplicate, or reordered fields are
invalid. A parser validates every field, canonically reserializes the value,
appends the LF, and requires exact byte equality. Pretty-printed, equivalently
escaped, non-canonical-number, or otherwise byte-distinct JSON is invalid.

The complete artifact is at most 67,108,864 bytes, including its final LF. It
contains at most 10,000 part records and at most 10,000 regional observations
in aggregate across all part records. Size and collection ceilings are
fail-closed preflight checks before expanded per-record, per-region, or
cross-record validation. No oversized input is truncated or partially
accepted.

JSON integers use the exact ranges declared below and are never represented as
strings or floating-point numbers. All comparisons are exact. Strings must
satisfy their field-level contracts before the bytes are canonical.

## Root object

The root has exactly these fields in this order:

| Field | Type | Contract |
| --- | --- | --- |
| `schema_name` | string | Exactly `circuitc.product_catalog_snapshot`. |
| `schema_version` | u32 | Exactly `1`. |
| `snapshot_id` | string | Non-empty canonical token matching the Design IR contract. |
| `observed_on` | string | Real Gregorian date in exact `YYYY-MM-DD` form. |
| `valid_through` | string | Real Gregorian date in exact `YYYY-MM-DD` form and not earlier than `observed_on`. |
| `source_uri` | string | Absolute HTTPS URI as constrained below. |
| `raw_source_sha256` | string | SHA-256 of the exact raw upstream-source bytes. |
| `parts` | array | Part records strictly sorted and unique by their exact identity key. |

`snapshot_id` uses the same canonical-token form as Design IR: non-empty,
without surrounding whitespace or control characters. Both dates must denote
real calendar dates, including leap-year rules; lexical shape alone is not
sufficient. Date comparison is chronological.

`source_uri` is ASCII and has the exact lowercase prefix `https://`. Its host
uses non-empty lowercase ASCII DNS labels, optionally followed by a canonical
nonzero decimal port other than `443`; IPv6-literal authority syntax is not
supported in v1. The URI has no user information, fragment, whitespace,
control character, backslash, raw character outside the RFC 3986 path/query
grammar, or `.` or `..` path segment. A percent escape uses exactly two
uppercase hexadecimal digits and must not encode an RFC 3986 unreserved ASCII
character. Other schemes and non-canonical equivalent URI spellings, including
leading-zero ports, are invalid. The URI is traceability, not a build input to
fetch.

`raw_source_sha256` is exactly 64 lowercase hexadecimal characters. The
snapshot parser validates its spelling but does not fetch or authenticate the
raw source. The URI and digest do not independently prove external truth or
upstream authenticity unless the exact raw bytes are separately retained and
verified.

## Part records

Each part record has exactly these fields in this order:

| Field | Type | Contract |
| --- | --- | --- |
| `logical_function` | string | Exact canonical logical-function token. |
| `manufacturer` | string | Non-empty canonical text. |
| `manufacturer_part_number` | string | Non-empty canonical text. |
| `package` | string | Non-empty canonical text. |
| `value` | object | Exact typed value below. |
| `lifecycle` | string enum | `active`, `not_recommended_for_new_designs`, or `obsolete`. |
| `availability` | array | Regional observations strictly sorted and unique by `region`. |

Canonical text is non-empty UTF-8 with no surrounding whitespace or control
characters. A logical-function token follows the Design IR canonical-token
contract. Snapshot v1 supports the exact pairs `resistor` with a `resistance`
value and `dc_voltage_source` with a `dc_voltage` value. Other functions or
function/value-kind pairs are unsupported rather than approximated.

Part records are strictly increasing in lexicographic UTF-8 byte order by the
exact `(logical_function, manufacturer, manufacturer_part_number, package)`
tuple. That tuple is also the uniqueness key: two records may not claim the
same identity with different value, lifecycle, or regional observations.

## Exact typed value

The value object has exactly these fields in this order:

| Field | Type | Contract |
| --- | --- | --- |
| `kind` | string enum | `resistance` or `dc_voltage`. |
| `coefficient` | i64 | Signed exact decimal coefficient. |
| `exponent` | i8 | Base-ten exponent in the Design IR range `-18..=18`. |
| `unit` | string enum | Exactly `ohm` for `resistance`; exactly `volt` for `dc_voltage`. |

The represented quantity is `coefficient * 10^exponent` in the named SI unit.
It uses the Design IR canonical decimal form: zero is exactly coefficient `0`
and exponent `0`; otherwise trailing decimal zeros are folded from the
coefficient into the exponent while the result remains representable and the
exponent is below `18`. Resistance must be strictly positive. DC voltage may
be signed. No binary floating-point conversion participates in validation,
ordering, compatibility, or identity.

Exact value compatibility requires equality of kind, canonical coefficient,
canonical exponent, and unit. Numerically equal but non-canonical encodings are
invalid snapshot bytes rather than alternate spellings.

## Regional observations

Each regional observation has exactly these fields in this order:

| Field | Type | Contract |
| --- | --- | --- |
| `region` | string | Non-empty canonical region token matching the Design IR contract. |
| `available_quantity` | u64 | Exact observed available quantity; zero is permitted evidence. |
| `lead_time_days` | u32 | Exact observed lead time in calendar days; zero is permitted evidence. |

Within one part record, `availability` entries are strictly increasing in
lexicographic UTF-8 byte order by exact `region` and are therefore unique. An
empty availability array is contract-valid evidence but cannot satisfy a
physical component's required region. The sum of all availability-array
lengths is checked without overflow and must not exceed 10,000.

## Authentication and Design IR resolution

Resolution consumes one fully validated canonical snapshot and one fully
validated Design IR. A physical Design must carry one `CatalogEvidenceRef`.
The consumer rejects an artifact over the complete 64 MiB ceiling before
hashing or parsing it. Before resolving any part, the resolver:

1. computes SHA-256 over the exact snapshot bytes, including the final LF, and
   requires equality with `CatalogEvidenceRef.sha256`;
2. requires root `snapshot_id` to equal `CatalogEvidenceRef.snapshot_id`; and
3. requires `CatalogEvidenceRef.evaluated_on` to fall within the inclusive
   `[observed_on, valid_through]` interval.

The resolver then visits every primary physical part and every approved
substitution. An approved substitution inherits its component's logical
function, exact typed value, lifecycle requirement, and sourcing constraints.
The checked sum of primary and approved-substitution identities across all
physical components must not exceed 10,000; the resolver rejects a larger
request before building the resolved result or visiting individual identities.
It indexes the already sorted unique snapshot once and visits component paths
and alternate identities in canonical order, independent of caller collection
order.
Each requested identity must resolve to exactly one part record by exact
`(logical_function, manufacturer, manufacturer_part_number, package)` equality.
For each resolved record, all of the following are mandatory:

- logical function, manufacturer, manufacturer part number, and package equal
  the requested identity exactly;
- value kind, coefficient, exponent, and unit equal the component value
  exactly;
- observed lifecycle equals the authored lifecycle requirement exactly;
- one regional observation has exact `region` equality with
  `required_region`;
- `available_quantity >= minimum_available_quantity`; and
- `lead_time_days <= maximum_lead_time_days`.

There is no case folding, trimming, fuzzy matching, package substitution,
dimensional conversion, value tolerance, lifecycle ordering, region fallback,
or implicit alternate selection. Extra snapshot records are permitted but do
not become product intent and are absent from the resolved result.

## Failure behavior

Any structural, canonical-byte, resource-bound, authentication, date,
resolution, compatibility, lifecycle, or sourcing failure returns a stable
machine-readable `CC-CATALOG-*` diagnostic and no resolved catalog. Contract
and byte failures use the `CC-CATALOG-CONTRACT-*` family; digest, snapshot-ID,
and validity-interval failures use `CC-CATALOG-AUTH-*`; part and policy failures
use `CC-CATALOG-RESOLVE-*`.

Resolution is all-or-nothing. Consumers may not return a partial map, silently
drop an unresolved primary or alternate, select a nearby record, consult the
network or host clock, or reinterpret an unknown field or enum value.

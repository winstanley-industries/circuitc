# CircuitC Design IR v1

## Status

Version 1 is the active, unreleased bootstrap in-memory contract. It is not a
serialized wire format. Until CircuitC publishes its first released schema,
this contract evolves in place: fields, meanings, and identities may change
without a schema-version bump, backwards-compatibility work, or migrations.
Semantic changes must still be documented here and in an ADR when they affect
compiler boundaries, authority, determinism, or backend ownership.

## Root

A `Design` contains:

- `schema_version`, exactly `1`;
- `name`, a stable design namespace and safe single-file artifact stem that
  starts with an ASCII letter or underscore and contains only ASCII letters,
  digits, underscores, or hyphens;
- named `nets`, with exactly one optional simulation ground;
- an elaborated module-instance hierarchy with typed ports;
- `components`, each with a unique semantic path and reference;
- zero or more typed simulation `analyses`, each with a unique semantic path;
- zero or more typed numerical `assertions`, each bound to one declared
  analysis and net; and
- a `board` with an exact rectangular outline and explicitly identified route
  segments.

## Coordinates

Every coordinate and size is a signed 64-bit integer count of nanometres. Sizes
and route widths are strictly positive. The current accepted absolute envelope
is 1,000,000,000,000 nm and applies to stored and derived values, including the
outline far corner and transformed pad centres. Backend arithmetic is checked
before scaling. Invalid public Rust values produce diagnostics, not panics.
Orthogonal rotation is counterclockwise as rendered; in KiCad's Y-down frame,
an offset `(x, y)` at 90 degrees maps to `(y, -x)`.

## Quantities

An electrical quantity is:

- a signed 64-bit decimal coefficient;
- a base-ten exponent in `[-18, 18]`; and
- a physical unit tag.

The represented value is `coefficient * 10^exponent` in the named SI unit.
There is no floating-point value in the canonical representation. Canonical
values fold trailing coefficient zeros into the largest exact exponent no
greater than `18`; values written with larger exponents fold exact zeros back
into the coefficient. Zero is represented with coefficient and exponent zero.
This makes equivalent base-unit and prefixed-unit source forms structurally
equal. Backends may format the canonical value with an engineering exponent.
The v1 unit tags are ohm, volt, ampere, farad, henry, hertz, second, degree,
and dimensionless. Frequency, time, and phase remain exact quantities in the
canonical IR; a simulator backend is the first boundary allowed to lower them
to floating point.

## Nets and connections

Net names are unique non-empty canonical tokens. Every logical symbol pin has
exactly one explicit connection state: connected to one declared canonical net
or intentionally no-connect. No-connect is a typed state, never a magic net
name. Physical pads resolve through explicit pin-to-pad bindings; every pad has
exactly one binding, a logical pin may bind to multiple pads, and every
connected logical pin on a physical component has at least one bound pad. A
no-connect pad remains absent from canonical Design IR nets. A backend may
lower that state to a host-specific placeholder net when the host requires one
to preserve connectivity parity; that placeholder is derived and never enters
canonical intent. Simulation model pins resolve through the logical mapping,
must be connected, and the model's two terminals must be distinct.

SPICE names are backend identities. Lowering accounts for simulator grammar,
case-folding, and reserved ground aliases and exposes a reversible mapping to
canonical net and component identities.

## Hierarchy and interfaces

The M1B contract stores the elaborated instance tree rather than reusable
source templates. Each module instance has a unique semantic path. A dotted
child path requires its parent, and a component belongs to the module named by
the parent of its semantic path. Module ports have a unique local name, an
input/output/inout direction, an electrical pin type, and an explicit
connected or no-connect state.

The instance tree preserves hierarchy and typed interface intent without
embedding KiCad sheets. In M1B, the KiCad and SPICE backends consume module
paths for component ownership only. Module-port direction, electrical type,
and connection state are validated but are not yet lowered into either backend;
ports reference existing nets and do not add connectivity of their own. A later
parameterized module language must elaborate to this same form.

## Components

A component always has one exact typed electrical value and has one or both of:

- a physical implementation: KiCad library identifier, exact pad geometry,
  and code-authored placement; or
- a simulation primitive with explicit terminal-to-pin mapping.

The v1 simulation subset contains resistors and independent DC voltage sources.
Unsupported devices are rejected rather than approximated.

Every component additionally carries:

- an explicit logical device identity;
- either a manufacturer plus manufacturer part number, or an explicit virtual
  identity for a non-physical part;
- an exact typed resistance or DC-voltage value independent of whether a
  simulation model is attached;
- a KiCad symbol library identifier and an injective logical-pin-to-symbol-pin
  binding with electrical pin types;
- a source-authored schematic position and orthogonal rotation; and
- for simulation, an explicit backend model identifier in addition to its
  terminal-to-logical-pin mapping.

In v1 the logical device identity is one of `resistor` or
`dc_voltage_source`, and the simulation model identifier is one of `spice:R`
or `spice:Vdc`. Other values are rejected with `CC-VALUE-003`, `CC-SIM-010`,
or `CC-SIM-011` rather than being approximated.

Every physical component requires a manufacturer identity and manufacturer part
number whose full tuple with the logical device resolves to one catalog entry.
Virtual parts likewise resolve through an explicit catalog tuple with absent
manufacturer fields. Symbol, footprint, pad, and model identifiers are resolved
and validated independently; display names never imply a binding.
Component schematic anchors must be unique. During KiCad lowering, transformed
symbol connection points must also remain distinct unless their canonical
connection states are identical and connected. Coincident no-connect pins are
rejected rather than merged, and conflicting points fail before artifact
emission rather than merging canonical nets in the schematic projection.
The Design IR permits explicit logical-to-symbol and logical-to-pad mappings.
The initial KiCad 10 catalog subset can represent only bindings whose symbol
pin number equals every corresponding pad number; its backend rejects other
valid IR mappings with `CC-KICAD-BIND-001` rather than silently changing
connectivity. A later catalog contract may add an explicit pin-equivalence map.
KiCad silkscreen and courtyard drawings remain vendored backend catalog data;
they are copied into board output with derived identities and do not enter the
canonical Design IR. Every selected catalog symbol or footprint must resolve to
a publishable vendored library file, and every selected footprint must resolve
to drawing geometry; the compiled bundle carries these files as a sorted,
design-derived collection rather than a fixed singleton.

## Simulation analyses and assertions

Simulation intent is explicit and independent of whether components carry
simulation models. A design with simulation models and no analyses is valid;
canonicalization and compilation never synthesize an analysis or assertion.
Once any analysis is declared, every component with an electrically connected
logical pin must carry an explicit supported simulation model. An uncovered
component is a capability failure rather than being silently omitted from a
netlist. A design with analyses also requires exactly one simulation ground.

Each analysis has a unique canonical semantic `path` and exactly one kind:

- DC operating point has no numeric parameters and produces scalar samples.
- AC linear sweep names the semantic path of a component whose explicit model
  is a DC voltage source. It carries `points` in `2..=10,000`, strictly
  positive ordered `start_frequency` and `stop_frequency` quantities in hertz,
  a non-negative source `magnitude` in volts, and a `phase` in degrees.
- Transient carries a strictly positive `step` and `stop`, a non-negative
  `start` not greater than `stop`, all in seconds, plus an explicit `uic`
  boolean. The pinned backend's v1 R/Vdc subset integrates from time zero even
  when `start` filters later output, so Design validation budgets
  `ceil(stop / step) + 1` compute steps and rejects a budget over 10,000.
  `start` never reduces this resource bound.

The Design IR contains at most 256 analyses. No one analysis may request more
than 10,000 samples or compute steps, and the deterministic aggregate across
all analyses may not exceed 10,000: DC contributes one, AC contributes
`points`, and transient contributes `ceil(stop / step) + 1`. Aggregate
addition is checked and saturating. Numeric range, ordering, workload, and
grid-size checks compare exact decimals without floating-point conversion or
fixed-width scaled-integer overflow, independent of analysis declaration
order.
Analysis collection overflow is `CC-SIM-ANALYSIS-011`; transient compute-step
overflow remains the distinct `CC-SIM-ANALYSIS-010` diagnostic, and aggregate
workload overflow is `CC-SIM-ANALYSIS-012` at `design.analyses`.

Each assertion has a unique canonical semantic `path`, an `analysis_path`, a
declared canonical `net`, a typed sample, an expected voltage, an absolute
voltage tolerance, and a dimensionless relative tolerance. Expected values and
tolerances are exact canonical quantities; tolerances are non-negative. The
sample is scalar for DC, a hertz quantity for AC, or a seconds quantity for
transient. Frequency and time samples must lie within their analysis's
inclusive range and exactly name a sample the selected backend emits. AC
samples are members of the endpoint-inclusive linear grid: for a sample `x`,
`(x - start_frequency) * (points - 1)` is exactly divisible by
`stop_frequency - start_frequency`. For the pinned transient backend and v1
R/Vdc subset, accepted output times are zero-anchored integer multiples of
`step` filtered by `start`, plus the exact forced `stop` endpoint when it is
off-grid. Transient samples therefore must be a zero-anchored step multiple or
exactly `stop`; they are not interpreted as `start + k * step`. Sample kinds
cannot be reinterpreted across analysis kinds. The Design IR contains at most
10,000 assertions; collection overflow is `CC-SIM-ASSERTION-011`.

Analyses and assertions are sorted by semantic path followed by their exact
fields. Their quantities are canonicalized before sorting, so declaration
permutations and equivalent decimal spellings produce equal canonical IR.

## Routes

A route segment has a unique semantic path independent of geometry and names
one declared net, a copper layer, exact endpoints, and a positive width.
Otherwise identical reversed segments are duplicate geometry. Version 1
validates bounds and identity but delegates complete connectivity and clearance
checking to the host KiCad DRC. APGAR lowering is not part of this schema
version.

## Identity and canonicalization

Backend UUIDs derive from the design name plus domain-tagged, length-prefixed
semantic identity fields using the CircuitC UUIDv8 derivation. CircuitC checks
global emitted UUID uniqueness and global uniqueness of the rendered semantic
paths used by identity manifests. Entity paths and references are unique. Writers
sort unordered collections by stable semantic keys before emission. Language
elaboration also canonicalizes unordered net, module, port, component,
connection, symbol-pin binding, pad, pin-to-pad binding, and route vectors so
declaration permutations are equal at the canonical IR boundary, not only
after backend emission. Simulation analysis and assertion vectors follow the
same rule, sorting by semantic path and exact typed fields.

The language frontend retains source spans in an elaboration provenance side
table keyed by semantic path. Requested source filenames are diagnostic I/O
metadata; deterministic identity manifests use the logical design-derived
source name. Parser-specific nodes and source filenames are not embedded in
Design IR values and do not participate in backend identity.

# CircuitC Design IR v1

## Status

Version 1 is the active, unreleased bootstrap in-memory contract. It is not a
serialized wire format. Until CircuitC publishes its first released schema,
this contract evolves in place: fields, meanings, and identities may change
without a schema-version bump, backwards-compatibility work, or migrations.
Semantic changes must still be documented here and in an ADR when they affect
compiler boundaries, authority, determinism, or backend ownership.

## Root

A `Design` contains:

- `schema_version`, exactly `1`;
- `name`, a stable design namespace and safe single-file artifact stem that
  starts with an ASCII letter or underscore and contains only ASCII letters,
  digits, underscores, or hyphens;
- named `nets`, with exactly one optional simulation ground;
- an elaborated module-instance hierarchy with typed ports;
- `components`, each with a unique semantic path and reference;
- zero or more typed simulation `analyses`, each with a unique semantic path;
- zero or more typed numerical `assertions`, each bound to one declared
  analysis and net;
- a `board` with an exact rectangular outline, explicitly identified route
  segments, and zero or one planar autoroute request; and
- `product`, a `ProductIntent` containing an optional pinned catalog-evidence
  reference, product variants, and manufacturability analyses.

## Coordinates

Every coordinate and size is a signed 64-bit integer count of nanometres. Sizes,
route widths, and autoroute width, clearance, and grid values are strictly
positive. The current accepted absolute envelope is 1,000,000,000,000 nm and
applies to stored and derived values, including the outline far corner and
transformed pad centres. Backend arithmetic is checked before scaling. Invalid
public Rust values produce diagnostics, not panics.
Orthogonal rotation is counterclockwise as rendered; in KiCad's Y-down frame,
an offset `(x, y)` at 90 degrees maps to `(y, -x)`.

## Quantities

An electrical quantity is:

- a signed 64-bit decimal coefficient;
- a base-ten exponent in `[-18, 18]`; and
- a physical unit tag.

The represented value is `coefficient * 10^exponent` in the named SI unit.
There is no floating-point value in the canonical representation. Canonical
values fold trailing coefficient zeros into the largest exact exponent no
greater than `18`; values written with larger exponents fold exact zeros back
into the coefficient. Zero is represented with coefficient and exponent zero.
This makes equivalent base-unit and prefixed-unit source forms structurally
equal. Backends may format the canonical value with an engineering exponent.
The v1 unit tags are ohm, volt, ampere, farad, henry, hertz, second, degree,
and dimensionless. Frequency, time, and phase remain exact quantities in the
canonical IR; a simulator backend is the first boundary allowed to lower them
to floating point.

## Nets and connections

Net names are unique non-empty canonical tokens. Every logical symbol pin has
exactly one explicit connection state: connected to one declared canonical net
or intentionally no-connect. No-connect is a typed state, never a magic net
name. Physical pads resolve through explicit pin-to-pad bindings; every pad has
exactly one binding, a logical pin may bind to multiple pads, and every
connected logical pin on a physical component has at least one bound pad. A
no-connect pad remains absent from canonical Design IR nets. A backend may
lower that state to a host-specific placeholder net when the host requires one
to preserve connectivity parity; that placeholder is derived and never enters
canonical intent. Simulation model pins resolve through the logical mapping,
must be connected, and the model's two terminals must be distinct.

SPICE names are backend identities. Lowering accounts for simulator grammar,
case-folding, and reserved ground aliases and exposes a reversible mapping to
canonical net and component identities.

## Hierarchy and interfaces

The M1B contract stores the elaborated instance tree rather than reusable
source templates. Each module instance has a unique semantic path. A dotted
child path requires its parent, and a component belongs to the module named by
the parent of its semantic path. Module ports have a unique local name, an
input/output/inout direction, an electrical pin type, and an explicit
connected or no-connect state.

The instance tree preserves hierarchy and typed interface intent without
embedding KiCad sheets. In M1B, the KiCad and SPICE backends consume module
paths for component ownership only. Module-port direction, electrical type,
and connection state are validated but are not yet lowered into either backend;
ports reference existing nets and do not add connectivity of their own. A later
parameterized module language must elaborate to this same form.

## Components

A component always has one exact typed electrical value and has one or both of:

- a physical implementation: KiCad library identifier, exact pad geometry,
  and code-authored placement; or
- a simulation primitive with explicit terminal-to-pin mapping.

The v1 simulation subset contains resistors and independent DC voltage sources.
Unsupported devices are rejected rather than approximated.

Every component additionally carries:

- an explicit logical-function identity;
- for a physical part, manufacturer, manufacturer part number, package,
  lifecycle requirement, sourcing constraints, and approved substitutions;
- for a non-physical part, an explicit virtual identity that omits every
  physical product field;
- an exact typed resistance or DC-voltage value independent of whether a
  simulation model is attached;
- a KiCad symbol library identifier and an injective logical-pin-to-symbol-pin
  binding with electrical pin types;
- a source-authored schematic position and orthogonal rotation; and
- for simulation, an explicit backend model identifier in addition to its
  terminal-to-logical-pin mapping.

In v1 the logical-function identity is one of `resistor` or
`dc_voltage_source`, and the simulation model identifier is one of `spice:R`
or `spice:Vdc`. Other values are rejected with `CC-VALUE-003`, `CC-SIM-010`,
or `CC-SIM-011` rather than being approximated.

Every physical component requires a manufacturer identity and manufacturer part
number whose full tuple with the logical function resolves to one catalog entry.
It also requires a non-empty canonical package string without surrounding
whitespace or control characters; a lifecycle requirement
of `active`, `not_recommended_for_new_designs`, or `obsolete`; positive
`minimum_available_quantity: u64` and `maximum_lead_time_days: u32` sourcing
constraints; and a non-empty canonical `required_region` token. Approved
substitutions contain at most 256 entries and are sorted and unique by the
exact `(manufacturer, manufacturer_part_number, package)` tuple. Each
substitution has non-empty manufacturer, manufacturer-part-number, and package
strings without surrounding whitespace or control characters. Its package
must exactly equal the primary part's package. The exact primary
`(manufacturer, manufacturer_part_number, package)` tuple is an invalid
self-substitution, not an approved alternate. Package equality is a structural
Design IR rule only; a later authenticated catalog-evidence contract must
independently prove logical-function and authored-value compatibility.
Virtual parts likewise resolve through an explicit catalog tuple with absent
manufacturer fields. They also omit package, lifecycle requirement, sourcing
constraints, and approved substitutions. Symbol, footprint, pad, and model
identifiers are resolved and validated independently; display names never
imply a binding.
Component schematic anchors must be unique. During KiCad lowering, transformed
symbol connection points must also remain distinct unless their canonical
connection states are identical and connected. Coincident no-connect pins are
rejected rather than merged, and conflicting points fail before artifact
emission rather than merging canonical nets in the schematic projection.
The Design IR permits explicit logical-to-symbol and logical-to-pad mappings.
The initial KiCad 10 catalog subset can represent only bindings whose symbol
pin number equals every corresponding pad number; its backend rejects other
valid IR mappings with `CC-KICAD-BIND-001` rather than silently changing
connectivity. A later catalog contract may add an explicit pin-equivalence map.
KiCad silkscreen and courtyard drawings remain vendored backend catalog data;
they are copied into board output with derived identities and do not enter the
canonical Design IR. Every selected catalog symbol or footprint must resolve to
a publishable vendored library file, and every selected footprint must resolve
to drawing geometry; the compiled bundle carries these files as a sorted,
design-derived collection rather than a fixed singleton.

## Product intent, variants, and manufacturability

`ProductIntent` contains:

- `catalog`, either `null` or one `CatalogEvidenceRef`;
- zero or more `variants`; and
- zero or more `manufacturability_analyses`.

The collection and validation-workload ceilings are:

- at most 256 approved substitutions per physical part;
- at most 256 variants per Design;
- at most 10,000 for the checked sum of
  `physical_component_count * variant_count` totality work and the aggregate
  number of submitted variant component-state entries;
- at most 256 configuration entries per variant;
- at most 128 UTF-8 bytes per configuration key and 4096 UTF-8 bytes per
  configuration value;
- at most 256 manufacturability analyses per Design; and
- at most 10,000 manufacturability assertions in aggregate across the Design.

Validation checks collection counts, checked aggregate workloads, and UTF-8
byte ceilings before expanded membership, variant-totality, per-entry
semantic, or cross-entry validation. Exceeding a ceiling is a fail-closed
diagnostic; no collection is truncated and no oversized input is partially
accepted.

A design with at least one physical component requires a non-null catalog
evidence reference and at least one variant. A virtual-only design may leave
the reference null and both collections empty. The reference identifies
evidence; it does not embed remote catalog observations into canonical Design
IR.

`CatalogEvidenceRef` contains exactly:

- `snapshot_id`, a non-empty canonical token;
- `sha256`, exactly 64 lowercase hexadecimal characters identifying the exact
  canonical `circuitc.product_catalog_snapshot` v1 bytes, including their final
  LF; and
- `evaluated_on`, an authored, calendar-valid date in exact `YYYY-MM-DD` form.

The evaluated date is canonical authored input. Validation and future release
freshness decisions may consume only authenticated evidence plus explicit
authored policy. Wall-clock time and live network state are never inputs to
canonicalization, validation, or artifact identity.

Catalog verification consumes the separate
[`product_catalog_snapshot/v1`](../product_catalog_snapshot/v1.md) artifact; no
remote observations are copied into Design IR. The exact snapshot digest and
ID must match this reference, and `evaluated_on` must lie within the snapshot's
inclusive `[observed_on, valid_through]` interval. Every primary physical part
and approved alternate must resolve to exactly one catalog record and satisfy
exact logical-function, package, typed-value, lifecycle, required-region,
minimum-quantity, and maximum-lead-time checks. Failure returns no partial
resolution and does not mutate canonical Design IR.

Each variant contains:

- a unique canonical semantic `path`;
- a strictly positive `build_quantity: u64`;
- `components`, containing exactly one state entry for every physical
  component and no entry for a virtual component; and
- `configurations`, a collection with canonical-token keys, non-empty
  canonical-text values, and unique keys. It contains at most 256 entries;
  each key contains at most 128 UTF-8 bytes and each value at most 4096 UTF-8
  bytes.

A component state names the component semantic path and is exactly one of:

- `fitted`, which selects the component's primary physical part;
- `not_fitted`; or
- `alternate`, which contains an exact `(manufacturer,
  manufacturer_part_number, package)` tuple equal to one of that component's
  approved substitutions.

An alternate cannot be inferred by package compatibility, manufacturer name,
display value, footprint, or catalog recommendation. Unknown components,
missing or duplicate physical-component states, states for virtual components,
unapproved alternate tuples, exact-primary self-substitutions, and
cross-package substitutions are invalid canonical intent. A later catalog
contract must prove logical-function and authored-value compatibility; an
approved tuple alone does not constitute that evidence.

Each manufacturability analysis contains:

- a unique canonical semantic `path`;
- `adapter`, exactly `kicad`;
- `version`, exactly the string `10`; and
- `assertions`, sorted and unique by assertion semantic path.

A Design contains at most 256 analyses and at most 10,000 assertions in
aggregate across them. These aggregate ceilings are checked before expanded
assertion validation.

Every manufacturability assertion has a stable canonical semantic `path` and
one kind from the closed set `erc_clean`, `drc_clean`, `unconnected_clean`,
`schematic_parity_clean`, or `fabrication_inventory_complete`. Assertion paths
are globally unique within the analysis collection, and a path cannot appear
with two kinds. An analysis may contain each assertion kind at most once. These
values author requested capability and acceptance intent; they do not claim
that KiCad manufacturing export, normalized result/report contracts, or
release publication already exist.

## Simulation analyses and assertions

Simulation intent is explicit and independent of whether components carry
simulation models. A design with simulation models and no analyses is valid;
canonicalization and compilation never synthesize an analysis or assertion.
Once any analysis is declared, every component with an electrically connected
logical pin must carry an explicit supported simulation model. An uncovered
component is a capability failure rather than being silently omitted from a
netlist. A design with analyses also requires exactly one simulation ground.

Each analysis has a unique canonical semantic `path` and exactly one kind:

- DC operating point has no numeric parameters and produces scalar samples.
- AC linear sweep names the semantic path of a component whose explicit model
  is a DC voltage source. It carries `points` in `2..=10,000`, strictly
  positive ordered `start_frequency` and `stop_frequency` quantities in hertz,
  a non-negative source `magnitude` in volts, and a `phase` in degrees.
- Transient carries a strictly positive `step` and `stop`, a non-negative
  `start` not greater than `stop`, all in seconds, plus an explicit `uic`
  boolean. The pinned backend's v1 R/Vdc subset integrates from time zero even
  when `start` filters later output, so Design validation budgets the declared
  nominal grid as `ceil(stop / step) + 1` samples and rejects a budget over
  10,000. `start` never reduces this declaration bound. The backend is adaptive,
  so this count is not a promise about accepted/rejected solver steps; the
  process adapter separately enforces runtime resource limits and validates the
  axis that was actually emitted.

The Design IR contains at most 256 analyses. No one analysis may request more
than 10,000 nominal samples, and the deterministic declared aggregate across
all analyses may not exceed 10,000: DC contributes one, AC contributes
`points`, and transient contributes `ceil(stop / step) + 1`. Aggregate addition
is checked and saturating. Numeric range, ordering, declared workload, and grid
size checks compare exact decimals without floating-point conversion or
fixed-width scaled-integer overflow, independent of analysis declaration order.
Analysis collection overflow is `CC-SIM-ANALYSIS-011`; transient nominal-grid
overflow remains the distinct `CC-SIM-ANALYSIS-010` diagnostic, and aggregate
declared-grid overflow is `CC-SIM-ANALYSIS-012` at `design.analyses`.

Each assertion has a unique canonical semantic `path`, an `analysis_path`, a
declared canonical `net`, a typed sample, an expected voltage, an absolute
voltage tolerance, and a dimensionless relative tolerance. Expected values and
tolerances are exact canonical quantities; tolerances are non-negative. The
sample is scalar for DC, a hertz quantity for AC, or a seconds quantity for
transient. Frequency and time samples must lie within their analysis's
inclusive range. AC samples are members of the endpoint-inclusive linear grid:
for a sample `x`,
`(x - start_frequency) * (points - 1)` is exactly divisible by
`stop_frequency - start_frequency`. A transient sample is restricted to the
authored nominal grid: a zero-anchored step multiple or exactly `stop`, never
`start + k * step`. This restriction is canonical intent, not a claim that the
adaptive backend will emit that row. Checked execution must observe the exact
lowered assertion time and declared stop in the actual result axis or fail the
analysis. Sample kinds cannot be reinterpreted across analysis kinds. The
Design IR contains at most 10,000 assertions; collection overflow is
`CC-SIM-ASSERTION-011`.

Analyses and assertions are sorted by semantic path followed by their exact
fields. Their quantities are canonicalized before sorting, so declaration
permutations and equivalent decimal spellings produce equal canonical IR.

## Routes and autorouting intent

A route segment has a unique semantic path independent of geometry and names
one declared net, a copper layer, exact endpoints, and a positive width.
Otherwise identical reversed segments are duplicate geometry. Version 1
validates bounds and identity but delegates complete connectivity and clearance
checking to the host KiCad DRC. A source-authored route segment is canonical
copper and remains independent of APGAR route search.

A board contains zero or one planar autoroute request. The request has a unique
semantic path, names one declared net and one front or back copper layer, and
carries positive exact width, clearance, and grid values in integer
nanometres. The grid is anchored at the board-outline origin, and each terminal
pad centre must lie on that exact lattice. The request is unresolved routing
intent, not a route segment, and therefore does not become KiCad copper merely
by being present in the Design IR.

The initial capability admits only a net with exactly two physical terminal
pads and one selected layer. Its deterministic CPU result may contain only a
continuous chain of horizontal, vertical, or 45-degree segments. Vias, arcs,
multipin routing, other headings, and approximation of unsupported geometry or
rules are outside this contract and fail with machine-readable diagnostics.

APGAR lowering crosses a separate versioned process contract. It converts
nanometres to APGAR's current 2,000,000-database-units-per-millimetre domain by
checked multiplication by two. Import requires every returned coordinate and
width to be exactly divisible by two and within the Design IR envelope. A
selected result becomes canonical physical intent only after its strict
versioned JSON contract and exact request association are authenticated, its
APGAR admission status is verified, and its geometry is losslessly imported
into a fresh validated Design IR. APGAR exact admission and KiCad DRC remain
separate required authorities for accepting that imported route.

## Identity and canonicalization

Backend UUIDs derive from the design name plus domain-tagged, length-prefixed
semantic identity fields using the CircuitC UUIDv8 derivation. CircuitC checks
global emitted UUID uniqueness and global uniqueness of the rendered semantic
paths used by identity manifests. Entity paths and references are unique. Writers
sort unordered collections by stable semantic keys before emission. Language
elaboration also canonicalizes unordered net, module, port, component,
connection, symbol-pin binding, pad, pin-to-pad binding, and route vectors so
declaration permutations are equal at the canonical IR boundary, not only
after backend emission. Simulation analysis and assertion vectors follow the
same rule, sorting by semantic path and exact typed fields.
Approved substitutions sort by exact manufacturer, manufacturer part number,
and package. Variants sort by path; their component states sort by component
path, and configuration entries sort by key then value. Manufacturability
analyses and their assertions sort by semantic path followed by their exact
fields. Equivalent declaration permutations therefore produce equal product
intent before any BOM, manufacturing, analysis, or release backend exists.

The language frontend retains source spans in an elaboration provenance side
table keyed by semantic path. Requested source filenames are diagnostic I/O
metadata; deterministic identity manifests use the logical design-derived
source name. Parser-specific nodes and source filenames are not embedded in
Design IR values and do not participate in backend identity.

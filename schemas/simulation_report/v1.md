# CircuitC simulation assertion report v1

## Status and authority

Version 1 records the checked assertion outcomes for one normalized simulation
result. The artifact uses strict canonical UTF-8 JSON with a final newline.
Unknown, missing, or duplicate fields are invalid. It binds the complete
request → map → result chain and never treats an omitted assertion as passing.
Every outcome must exactly match one digest-bound request assertion. Pass/fail
values additionally join to the exact signal, unit, axis sample, and value in
the authenticated normalized result.

Numbers use the finite canonical scientific-decimal encoding from the
normalized-result contract.

## Root object

| Field | Type | Contract |
| --- | --- | --- |
| `schema_name` | string | Exactly `circuitc.simulation_report`. |
| `schema_version` | integer | Exactly `1`. |
| `design` | string | Request design stem. |
| `analysis_path` | string | Request analysis semantic path. |
| `analysis_kind` | string enum | `dc_operating_point`, `ac_linear_sweep`, or `transient`; samples must use the corresponding scalar, frequency, or time axis. |
| `request_sha256` | string | Digest of exact canonical request bytes. |
| `map_sha256` | string | Digest of exact canonical map bytes. |
| `result_sha256` | string | Digest of exact canonical result bytes. |
| `assertions` | array | Exactly one outcome per request assertion, strictly sorted and unique by `path`. |
| `summary` | object | Exact status counts. |

## Assertion outcome

Each assertion has exactly:

| Field | Type | Contract |
| --- | --- | --- |
| `path` | string | Canonical assertion semantic path. |
| `status` | string enum | `pass`, `fail`, `unsupported`, or `unevaluated`. |
| `signal_kind` | string enum | One normalized-result signal kind. |
| `canonical_identity` | string | Canonical Design IR net token for voltage signals or component semantic path for branch signals. |
| `sample` | object | Exact `kind` plus canonical numeric `value` identifying scalar/frequency/time context. |
| `unit` | string enum | `volt`, `ampere`, or `degree`, matching `signal_kind`. |
| `expected` | string | Canonical expected value in `unit`. |
| `actual` | string or null | The field is always present: a string for pass/fail and null for unsupported/unevaluated. |
| `absolute_tolerance` | string | Canonical non-negative tolerance in `unit`. |
| `relative_tolerance` | string | Canonical non-negative dimensionless ratio. |
| `diagnostic` | object or null | The field is always present: a normalized `{code, message}` object for unsupported/unevaluated and optionally for pass/fail, otherwise null. |

The initial evaluator uses an inclusive bound:

```text
abs(actual - expected) <= absolute_tolerance
                           + relative_tolerance * abs(expected)
```

`pass` means that inclusive expression is true and `fail` means it is false;
the serialized status may not contradict the computed outcome. Its `actual`
value must equal the corresponding authenticated normalized-result value.
The report does not serialize a separate delta or allowed-bound field. Both
are deterministically recomputed from `actual`, `expected`,
`absolute_tolerance`, and `relative_tolerance` when the report is verified.

The source/Design IR retain exact expected values and tolerances until this
explicit floating-point result boundary.

## Summary object

The object has exactly the unsigned integer fields `pass`, `fail`,
`unsupported`, and `unevaluated`. Every value must equal the number of matching
assertion outcomes.

## Checked-phase behavior

The checked phase succeeds only when every per-analysis result has status
`completed` and every assertion outcome is `pass`. A completed result with no
assertions therefore succeeds vacuously. An `unsupported`, `failed`, or
`unevaluated` result with no assertions still fails the checked phase even
though its report has no outcomes.

`fail`, `unsupported`, and `unevaluated` remain explicit deterministic evidence
and cause the checked phase to fail. A runtime or mapping failure may therefore
produce unevaluated outcomes, but it may never silently drop them or convert
them to pass. A completed result authenticates only pass/fail outcomes. An
`unsupported` result authenticates only unsupported outcomes; failed and
unevaluated results authenticate only unevaluated outcomes. CircuitC evaluates
all authenticated assertions and executes every declared analysis in
semantic-path order rather than stopping when one outcome fails.

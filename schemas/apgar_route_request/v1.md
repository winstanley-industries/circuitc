# CircuitC APGAR route request v1

## Status and authority

Version 1 is CircuitC's strict process request for one planar APGAR routing
operation. CircuitC source and canonical Design IR remain authoritative. The
request is unresolved routing intent, not accepted copper, and it does not
serialize APGAR C++ layouts, `CompiledBoard`, opaque producer evidence, pointers,
or GPU state.

## Canonical JSON encoding

The artifact is UTF-8 compact JSON produced by `serde_json::to_string`, followed
by exactly one LF. There is no indentation or other whitespace. Struct fields
appear in the declaration order documented below; enum variants use the exact
lowercase `snake_case` strings listed here. Unknown, missing, or duplicate
fields are invalid. The parser deserializes, validates, reserializes, appends the
LF, and requires byte equality, so an otherwise equivalent pretty-printed or
reordered document is not canonical.

The complete artifact is limited to 67,108,864 bytes including its final LF.
All JSON integer fields use their Rust signed or unsigned integer range; entity
IDs and APGAR fingerprints are JSON integers, not hexadecimal strings. SHA-256
values are exactly 64 lowercase hexadecimal characters, APGAR source revisions
are exactly 40 lowercase hexadecimal characters, candidate/signature strings
are 32 lowercase hexadecimal characters, and candidate payload checksums are
16 lowercase hexadecimal characters.

## Root object

The root has exactly these fields in this order:

| Field | Type | Contract |
| --- | --- | --- |
| `schema_name` | string | Exactly `circuitc.apgar_route_request`. |
| `schema_version` | u32 | Exactly `1`. |
| `design_name` | string | Safe CircuitC design/artifact stem. |
| `design_fingerprint_sha256` | string | Digest identity of the current routing-relevant Design projection. |
| `request_path` | string | Canonical semantic path of the authored `autoroute`. |
| `request_identity_sha256` | string | Stable semantic request identity. |
| `expected_apgar_source_revision` | string | Required APGAR Git revision. |
| `expected_apgar_contract_identity` | string | Required portable APGAR process-contract token. |
| `dbu_per_millimeter` | i64 | Exactly `2000000`. |
| `board_revision` | u64 | Deterministic board revision carried into replay. |
| `adapter_name` | string | Non-empty portable ASCII adapter identity. |
| `adapter_version` | string | Non-empty portable ASCII adapter version. |
| `layers` | array | Exact layer records below. |
| `nets` | array | Exact net records below. |
| `terminals` | array | Exact physical terminal records below. |
| `obstacles` | array | Exact conservative obstacle records below. |
| `routing_profile` | object | APGAR Board IR routing profile below. |
| `compiler_profile` | object | APGAR compiler profile below. |
| `planar_route` | object | Endpoint, policy, and scheduling request below. |
| `resource_limits` | object | Explicit process/work bounds below. |
| `unsupported_host_rules` | array | Rules intentionally delegated to KiCad below. |

`design_name` begins with an ASCII letter or `_` and otherwise contains ASCII
letters, digits, `_`, or `-`. A semantic path is non-empty, dot-separated
without empty components, and uses only ASCII alphanumerics, `_`, `+`, `-`,
`.`, or `/`. Portable identity tokens additionally permit `:`. The contract
checks the fingerprints' spelling; request construction and later import bind
their values to the current Design and authored request.

## Common value objects

An entity reference has exactly numeric `id: u64` and `generation: u32`.
Definition IDs are nonzero, and layer, net, terminal, and obstacle definitions
are globally unique by the complete pair. References must join exactly; display
names never substitute for them.

A point has exactly numeric `x: i64` and `y: i64`. A box has exactly `min` and
`max` points. Coordinates must fit APGAR's inclusive
`[-1000000000000, 1000000000000]` DBU envelope and box minima may not exceed
maxima. Positive DBU sizes are in `1..=1000000000000`. CircuitC lowering uses
checked `nm * 2`; no floating point or rounding is part of this wire format.

## Layers, nets, terminals, and obstacles

Each layer has exactly `reference`, `routing_id: u32`, `name`,
`physical_order: i32`, `side`, and `routable`. `side` is `front` or `back`.
Request v1 contains exactly one layer and requires `routable: true`; the
CircuitC producer assigns the stable routing ID and side for the selected
authored layer.

Each net has exactly `reference`, `name`, and `terminals`. Request v1 contains
exactly one routed net. Its terminal-reference array is strictly sorted and
unique and exactly equals the root terminal records in their canonical order.

Each terminal has exactly `reference`, `net`, `component_path`, `pad`, `center`,
`connection_region`, and `layers`. Request v1 contains exactly two terminal
records, strictly sorted by reference. Both belong to the sole net, name the
sole routing layer, and have a centre contained by their normalized exact box.
Their boxes must lie inside the compiler ROI.

Each obstacle has exactly `reference`, `layer`, `bounds`, `owner_net`, and
`provenance`. `owner_net` is an entity reference or null. Obstacles are strictly
sorted by reference, name the sole layer, use a known owner when non-null, lie
inside the compiler ROI, and retain non-empty control-free provenance. They are
the conservative wire projection of applicable pads and authored copper; a
contract-valid obstacle does not by itself prove that the producer included
every current Design obstacle.

Root layer, net, terminal, obstacle, and unsupported-rule arrays, and each net's
terminal array, contain at most 10,000 entries. The stronger v1 cardinalities
above still apply.

## Routing and compiler profiles

`routing_profile` has exactly `net`, `nominal_width_dbu`, `clearance_dbu`,
`allowed_layers`, and `allowed_headings`. It binds the sole net, contains exactly
the sole layer, and carries positive width and clearance. Headings are strictly
ordered as `horizontal`, `vertical`, `diagonal45`; no other set is valid.

`compiler_profile` has exactly:

| Field | Type |
| --- | --- |
| `schema_version` | u32, exactly `1` |
| `lattice_origin` | point |
| `lattice_step_dbu` | positive i64 DBU |
| `tile_width_nodes` | nonzero u32 |
| `tile_height_nodes` | nonzero u32 |
| `compilation_roi` | box |
| `active_regions` | array of `{layer, bounds}` |
| `allowed_headings` | exact H/V/45 array |
| `costs` | `{orthogonal_step, diagonal_step, bend}` u32 values |

Orthogonal and diagonal costs are nonzero; bend may be zero. V1 has exactly one
active region, on the sole layer and inside the ROI. Terminal regions,
obstacles, and planar endpoints also lie in the ROI. The array is strictly
sorted and contains at most 10,000 entries. APGAR execution additionally
enforces its tile-dimension, represented-node, lattice, and compiled-association
limits; mere JSON typing is not a substitute for `CompileBoard`.

## Planar route, policy, and scheduling

`planar_route` has exactly `net`, `start`, `goal`, `start_layer`, `goal_layer`,
`candidate_policy`, and `scheduling`. It binds the same sole net and layer as
the routing profile. Start and goal are distinct, lie inside the ROI, and match
the two terminal centres.

The candidate policy has exactly `schema_version`, `objective`,
`deterministic_seed`, `candidate_ordinal`, `orthogonal_step_surcharge`,
`diagonal_step_surcharge`, `bend_surcharge`, `banned_resources`, and
`resource_penalties`. Schema version is `1`; objective is
`base_scalar_cost`, `length_biased`, `bend_biased`, or `resource_diverse`.
Each resource has exactly `layer`, `lattice_x`, `lattice_y`, and `direction`,
where direction is `east`, `north_east`, `north`, `north_west`, `west`,
`south_west`, `south`, or `south_east`. Each penalty has exactly `resource` and
nonzero `additional_cost`. Both arrays are strictly sorted and unique and each
contains at most 10,000 entries. APGAR policy normalization later rejects
missing/illegal compiled resources, conflicts, unsupported objectives, and
cost overflow.

Scheduling has exactly numeric `batch_identity: u64` and `query_identity: u64`.
The request schema preserves their exact values; trusted lowering derives them
deterministically rather than from time, randomness, PID, or collection order.

## Resource limits and delegated host rules

`resource_limits` has exactly numeric `timeout_milliseconds`, `stdout_bytes`,
`stderr_bytes`, `diagnostic_bytes`, `candidate_primitives`, and
`expanded_resource_edges`. Every value is nonzero. Stdout and stderr are each
at most the 64 MiB contract ceiling. The runner and APGAR adapter must enforce
these authenticated limits and may impose stricter platform limits; the schema
does not claim that a declared bound has already been enforced. A completed
result's expanded physical-edge footprint must not exceed this request value
and is also subject to the result contract's fixed 1,000,000-edge ceiling.

Each `unsupported_host_rules` entry has exactly `code` and `path`. Code is a
non-empty uppercase ASCII machine code containing only letters, digits, and
`-`; path is a canonical semantic path. The array is strictly sorted and unique.
These are explicitly delegated rules, not ignored or approximated checks.
Successful APGAR admission does not clear them; supported KiCad DRC,
connectivity, unconnected, and parity evidence remains separately required.

## Contract validation versus later binding

Parsing is already semantic validation, not merely JSON decoding. It enforces
the exact schema, canonical bytes, cardinalities, sorting, global definition
uniqueness, known references, one-net/one-layer/two-terminal relationships,
profile/endpoint agreement, ROI containment, H/V/45 capability, and resource
bounds described above.

A parsed request is nevertheless only structurally and relationally valid.
Before execution, the trusted lowering/runner must also rederive and compare the
design fingerprint, semantic request identity, APGAR revision and contract pin,
entity IDs, complete obstacle set, checked nanometre-to-DBU conversions,
compiler-profile policy, scheduling identities, and actual executable
provenance. APGAR then independently creates and validates Board IR, compiles
the board, normalizes policy, routes, reconstructs the canonical physical-edge
footprint and logical-byte accounting, and performs exact candidate admission.
Failure at any of those stages is a result failure, never accepted copper.

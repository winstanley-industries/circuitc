# CircuitC APGAR route result v1

## Status and encoding

Version 1 is the strict result for one APGAR route request. It is UTF-8 compact
JSON produced by `serde_json::to_string`, with no whitespace and exactly one
final LF. Field order is the Rust struct declaration order documented below.
Unknown, missing, duplicate, pretty-printed, reordered, trailing, or otherwise
non-canonical data is invalid. The complete result is limited to 67,108,864
bytes. Integer and hexadecimal representations follow the request contract.

The result records either admitted candidate evidence or a stable failure. A
successful process exit alone cannot create `completed`, and even `completed`
does not mean KiCad acceptance.

## Root object

The root has exactly these fields in this order:

| Field | Type | Contract |
| --- | --- | --- |
| `schema_name` | string | Exactly `circuitc.apgar_route_result`. |
| `schema_version` | u32 | Exactly `1`. |
| `request_sha256` | string | SHA-256 of exact canonical request bytes, including final LF. |
| `request_path` | string | Canonical authored request path. |
| `tool` | object | Actual process identity below. |
| `replay` | object | Stable replay associations below. |
| `outcome` | tagged object | Exactly one completed or failure variant below. |

`tool` has exactly `name`, `version`, `contract_identity`, `source_revision`,
`executable_sha256`, and `device_class`. Name, version, contract, and device
class are portable ASCII identity tokens. Source revision is 40 lowercase hex
and executable digest is 64 lowercase hex. Contract validation checks their
shape; import/runner binding checks their exact equality to the request's
expected APGAR pin and the configured executable provenance.

`replay` has exactly `design_fingerprint_sha256`,
`request_identity_sha256`, `board_revision`, `deterministic_seed`,
`batch_identity`, and `query_identity`. Digests are lowercase SHA-256 strings;
the remaining fields are u64 JSON integers. The object contains replay
associations, not authority to bypass fresh APGAR admission or KiCad DRC.

## Tagged outcome

`outcome` is an internally tagged enum. Its first field is `kind`.

A completed outcome has exactly:

```json
{"kind":"completed","selected_candidate_id":"<32 lowercase hex>","candidates":[]}
```

`candidates` contains 1 to 10,000 admitted-candidate objects. Candidate IDs are
unique, but array order is not semantic and need not be sorted. The explicit
selected ID must match exactly one candidate; changing array order does not
change selection. The selected candidate's seed, batch identity, and query
identity must equal `replay`.

A failure outcome has exactly:

```json
{"kind":"failure","status":"route_not_found","diagnostic":{"code":"CC-ROUTE-SEARCH-001","path":"planar_route","message":"no exact planar route exists"}}
```

Status is `invalid_request`, `unsupported`, `board_validation_failed`,
`compilation_failed`, `policy_rejected`, `route_not_found`,
`candidate_rejected`, `resource_limit_exceeded`, or `tool_failed`. Diagnostic
has exactly `code`, `path`, and `message`: an uppercase ASCII machine code, a
canonical semantic path, and non-empty control-free text. Completed-only fields
are invalid in failure and failure-only fields are invalid in completed.

## Admitted candidate

Each candidate has exactly these fields in order:

| Field | Type |
| --- | --- |
| `schema_major` | u16, exactly `1` |
| `schema_minor` | u16, exactly `0` |
| `id` | 32-character lowercase hexadecimal string |
| `net` | numeric `{id, generation}` entity reference |
| `intended_terminals` | array of exactly two entity references |
| `associations` | object below |
| `geometry_schema_version` | u32, exactly `1` |
| `resource_schema_version` | u32, exactly `1` |
| `policy` | candidate-policy object from the request schema |
| `policy_identity` | u64 JSON integer |
| `provenance` | object below |
| `geometry` | exact line array below |
| `resources` | canonical physical-edge span array below |
| `metrics` | object below |
| `constraints` | object below |
| `geometry_signature` | 32-character lowercase hexadecimal string |
| `resource_signature` | 32-character lowercase hexadecimal string |
| `payload_checksum` | 16-character lowercase hexadecimal string |
| `logical_bytes` | u64 JSON integer |

The two intended terminals are strictly sorted and distinct. `associations`
has exactly numeric `board_content_hash: u64`,
`compiler_profile_fingerprint: u64`, `geometry_compiler_version: u32`,
`routing_profile_fingerprint: u64`, and `rule_bucket_identity: u64`.

`provenance` has exactly `generator`, `generator_version`, `backend`,
`supported_device_class`, `deterministic_seed`, `batch_identity`,
`query_identity`, and `candidate_ordinal`. Generator is `cpu_a_star`,
`cuda_frontier`, or `cuda_sweep`; backend is `cpu` or `cuda`. Other values are
numeric except the portable device-class token. The initial trusted process is
bound later to the CPU A* / CPU / `cpu-reference-v1` combination; those exact
values are intentionally an import/tool-pin check rather than merely an enum
shape check.

## Geometry, metrics, and constraints

Each `geometry` element has exactly `layer: u32`, `start`, `end`, and
`width_dbu: i64`. Points use exact numeric `{x, y}` DBU values. The array has 1
to 10,000 elements. Contract validation requires positive in-envelope width,
in-envelope nonzero H/V/45 lines, and one continuous same-layer chain. It also
requires metrics line count to equal array length and via count to be zero.

Each `resources` element has exactly `layer: u32`, `lattice_x: i64`,
`lattice_y: i64`, `direction`, `edge_count: u32`, and `usage_units: u32`.
Direction is one of the canonical physical-edge directions `east`,
`north_east`, `north`, or `north_west`. Entries are strictly sorted and unique
by `(layer, lattice_x, lattice_y, direction)`. Each edge count is positive,
usage is exactly one, lattice coordinates fit the contract envelope, and the
array is non-empty with at most 10,000 spans. The checked sum of `edge_count`
is at most 1,000,000. These are APGAR's public compressed physical-edge
resources, not `CompiledBoard` storage or C++ memory layout.

`metrics` has exactly unsigned `scalar_policy_cost`, `intrinsic_base_cost`,
`orthogonal_step_count`, `diagonal_step_count`, `bend_count`,
`line_primitive_count`, `via_count`, `axis_aligned_length_dbu`, and
`diagonal_projection_dbu`.

`constraints` has exactly `supported_hard_constraints_satisfied`,
`unsupported_rules_remain`, `connected_intended_terminal_count`, and
`exact_validation_status`. Status is `passed`, `unsupported_geometry`,
`invalid_geometry`, or `exact_rule_violation`. A completed candidate is
contract-valid only with `true`, `false`, `2`, and `passed`, respectively.
This status covers APGAR's declared subset; it does not clear the request's
separately recorded unsupported host rules.

The policy object and its resource entries have exactly the request-schema
shape and enum spellings. The result intentionally carries APGAR's public
associations, provenance, physical-edge spans, metrics, signatures, payload
checksum, and logical-byte accounting without serializing compiled fields or
producer-evidence handles. `logical_bytes` is positive and no greater than
67,108,864 at contract-validation time. Before import, it must equal APGAR's
independently recomputed candidate-v1 logical payload size; it is not the JSON
document length.

## Contract validation versus import

Parsing validates canonical bytes, schema/version, digest and identifier
spellings, collection bounds, unique candidate IDs, explicit selection,
candidate schema versions, sorted intended terminals, policy shape, H/V/45
continuous geometry, a non-empty canonical bounded physical-edge footprint,
positive bounded logical-byte accounting, zero vias, passed exact status, and
replay equality with the selected candidate's seed/batch/query provenance.

A result can satisfy those standalone invariants and still be unsafe to import.
Import therefore rechecks it against the exact current request and Design:

1. `request_sha256` equals SHA-256 of the exact request bytes, `request_path`
   matches, and replay design/request fingerprints and board revision match.
2. Tool name, version/contract identity, source revision, executable digest,
   and device class match the configured pinned APGAR process; selected
   provenance is the allowed CPU producer combination.
3. Candidate net, terminal refs, policy, seed, scheduling identities, layer,
   width, first endpoint, and last endpoint match the request exactly.
4. Candidate associations, policy identity, physical-edge spans, signatures,
   metrics, constraints, payload checksum, and logical-byte count equal
   independent APGAR reconstruction for that same request rather than merely
   having valid field shapes. The expanded span count must also fit the
   authenticated request limit.
5. Every returned coordinate and width is even, divides by two without loss,
   and fits the Design IR nanometre envelope. Standalone result validation does
   not reject odd DBUs because APGAR's DBU schema can represent them.
6. The imported lines remain continuous, nonzero H/V/45, one-layer geometry;
   derived route paths are stable and do not collide with authored or imported
   physical identities. The fresh Design IR is canonicalized and fully
   revalidated before KiCad emission.

Only that authenticated, lossless import makes the selected route canonical
physical intent for the build. APGAR exact admission and supported KiCad DRC,
connectivity, unconnected, and parity reports remain separate required
authorities bound to the same imported geometry. A failure outcome, stale
binding, or merely contract-valid candidate is never accepted copper.
